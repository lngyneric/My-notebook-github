# 模型上下文协议（Model Context Protocol, MCP）

## TL;DR

模型上下文协议（MCP）是大语言模型与外部资源交互的**开放标准化接口**，基于客户端-服务器架构，统一规范了工具、资源、提示词三类核心元素的通信方式，解决了传统工具函数调用厂商绑定、集成复杂、难以复用的问题，适合构建复杂、可扩展、跨厂商的企业级智能体系统，能让大语言模型和智能体对接数据库、API、物联网设备等各类外部系统，实现动态获取信息、执行操作等能力。

## MCP 模式概览

MCP 是一个开放通用连接标准，核心目标是让任意大语言模型（如 Gemini、GPT、Claude 等）都能无缝接入任意外部系统、数据库、工具，无需为每个对接场景单独开发定制集成方案。

### 核心架构
MCP 基于**客户端-服务器**架构运行，定义了三类核心元素：
| 元素 | 说明 |
|------|------|
| 资源（Resource） | 静态数据，如 PDF 文件、数据库记录 |
| 工具（Tool） | 可执行的功能，如发送邮件、调用 API |
| 提示词（Prompt） | 交互模板，指导 LLM 正确与资源/工具交互 |

MCP 服务器对外暴露这些元素，由 MCP 客户端（可以是 LLM 宿主应用或 AI 智能体本身）消费使用，大幅降低了 LLM 集成到不同运行环境的复杂度。

### 设计注意事项
MCP 只是接口协议规范，实际效果高度依赖底层 API 的设计质量：
1. 不能仅对老旧 API 简单套壳，需要针对智能体需求优化：例如仅支持逐个查询工单的 API，会让智能体汇总大量高优先级工单时异常缓慢不准确，需要额外增加过滤、排序等确定性功能，帮助非确定性的智能体高效工作。
2. 需要保证输入输出对智能体友好：MCP 本身不强制要求数据格式兼容性，例如返回 PDF 文件的文档服务对无法解析 PDF 的智能体没有实际意义，更好的做法是返回 Markdown 等智能体可直接处理的文本格式。

> [!QUOTE] 原始引用
> AI 智能体无法神奇地取代传统的确定性工作流程，反而往往需要更强大的确定性支持才能成功。
> 设计 MCP 集成时，不能只关注连接机制，更要深入考虑数据交换的本质，才能确保真正的兼容性和实用性。

## MCP 与工具函数调用的区别

MCP 和工具函数调用都能让 LLM 调用外部能力，但二者在实现方式和抽象层级有本质差异：

| 特性 | 工具函数调用 | 模型上下文协议（MCP） |
|------|--------------|------------------------|
| 标准化程度 | 厂商专有实现，不同 LLM 提供商规范不兼容 | 开放标准化协议，推动不同 LLM 与工具间的互操作 |
| 功能范围 | LLM 直接调用特定预定义功能的机制 | 构建 LLM 与外部工具发现和通信的完整框架 |
| 系统架构 | LLM 与应用工具处理逻辑的点对点直接交互 | 客户端-服务器架构，一个 LLM 应用可对接多个 MCP 服务器 |
| 发现机制 | 在会话上下文中静态配置可用工具列表 | 支持工具能力的动态发现和查询 |
| 可复用性 | 工具集成与特定应用和 LLM 平台深度绑定 | 可独立部署可复用的 MCP 服务器，跨平台复用 |

通俗来说：工具函数调用相当于给 AI 定制了一套专用工具，适合固定任务场景；MCP 则相当于建立了一套通用标准化的接口基础设施，本身不提供工具，但允许任意兼容厂商的工具接入，构建可动态扩展的开放生态。

> [!QUOTE] 原始引用
> 对于功能需求简单的应用，专用工具集已足够；但对于需要高度适应性、涉及多系统复杂交互的 AI 应用，采用 MCP 这样的通用标准协议是构建可持续演进架构的关键。

## MCP 核心设计与关键考虑因素

### 核心组件与交互流程
完整的 MCP 系统包含四层组件，交互流程分为五步：
1. **大语言模型（LLM）**：系统的智能核心，负责处理用户请求、制定计划、判断何时需要调用外部能力
2. **MCP 客户端**：LLM 的包装层，作为中间人将 LLM 的意图转换为符合 MCP 标准的请求，负责发现、连接 MCP 服务器
3. **MCP 服务器**：对接外部世界的网关，向授权客户端开放工具、资源、提示模板，通常按领域划分（如数据库、邮件服务）
4. **可选第三方服务**：MCP 服务器实际对接的外部终端，是最终执行操作的实体（如数据库、SaaS 平台）

交互流程：
1. **发现阶段**：MCP 客户端代表 LLM 查询服务器能力，服务器返回包含工具、资源、提示词的能力清单
2. **请求构建**：LLM 确定需要调用的工具，构造包含工具名和参数的请求
3. **客户端通信**：MCP 客户端将请求按标准格式发送给对应 MCP 服务器
4. **服务器执行**：MCP 服务器验证身份和请求合法性，调用底层接口执行操作
5. **响应和上下文更新**：服务器返回标准化结果给客户端，客户端转发给 LLM 更新上下文，LLM 继续后续任务

### 其他关键考虑因素
| 维度 | 说明 |
|------|------|
| 可发现性 | 支持客户端动态查询服务器能力，适合无需重新部署即可适配新能力的智能体 |
| 安全性 | 必须包含完善的身份验证和权限控制，限定客户端可访问的资源和可执行操作 |
| 实现复杂度 | 虽然协议本身开放，但落地复杂度较高，目前已有厂商提供 SDK 简化开发（如 Anthropic、FastMCP） |
| 错误处理 | 需要明确定义错误格式，让 LLM 能理解失败原因并尝试替代方案 |
| 部署方式 | 可本地部署在智能体同机器（适合低延迟、敏感数据场景），也可远程部署（适合组织内共享扩展） |
| 调用模式 | 同时支持按需实时交互调用，也支持大规模批量处理 |
| 传输机制 | 本地交互采用基于 JSON-RPC 的标准输入输出实现进程间通信；远程连接采用 Streamable HTTP、SSE 等 Web 友好协议 |

## 典型应用场景

MCP 大幅拓展了 AI 和 LLM 的能力边界，典型应用场景包括：
1. **数据库集成**：让智能体通过自然语言直接查询、更新数据库中的结构化数据，例如查询 Google BigQuery 数据集生成报表
2. **生成式媒体编排**：支持智能体整合多种生成式媒体服务，调用图片、视频、语音、音乐生成接口完成动态内容创作
3. **外部 API 交互**：标准化调用任意外部 API，获取天气、股价等实时信息，对接 CRM 等业务系统
4. **基于推理的信息提取**：比传统搜索更精准，智能体可以深入文档提取直接回答问题的具体片段，而非返回整篇文档
5. **自定义工具开发**：开发者可以将企业内部专属功能、私有系统封装为 MCP 服务器，无需修改 LLM 即可供智能体调用
6. **标准化 LLM 与应用通信**：统一通信层，降低集成成本，促进不同 LLM 厂商和应用之间的互操作
7. **复杂工作流编排**：整合多个 MCP 服务的工具和数据，完成多步骤复杂任务，例如提取客户信息→生成营销图→撰写邮件→发送邮件全流程自动化
8. **物联网设备控制**：让 LLM 通过自然语言控制智能家居、工业传感器、机器人等物理设备
9. **金融服务自动化**：对接金融数据源、交易平台、合规系统，实现行情分析、交易执行、理财建议、
