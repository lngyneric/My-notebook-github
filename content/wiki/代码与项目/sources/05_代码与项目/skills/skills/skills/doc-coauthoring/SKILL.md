# Doc Co-Authoring 协作文档创作 Skill
> 来源路径：`raw/05_代码与项目/skills/skills/skills/doc-coauthoring/SKILL.md`

---

## TL;DR
Doc Co-Authoring 是一套结构化的协作文档创作工作流，用于引导用户共同编写各类文档（技术文档、提案、PRD、决策文档、RFC等），分为「上下文收集→迭代细化与结构搭建→读者测试」三个阶段，最终产出对读者清晰易懂的高质量结构化文档。

---

## 基本信息
| 属性 | 内容 |
|------|------|
| 名称 | `doc-coauthoring` |
| 触发条件 | 用户提及写文档、创建提案、起草规格等文档类任务，或用户提到PRD/设计文档/决策文档/RFC等特定文档类型，或用户需要启动大型写作任务 |
| 适用场景 | 编写文档、提案、技术规格、决策文档等各类结构化内容，帮助高效传递上下文、迭代优化内容、验证文档对读者的可读性 |

---

## 工作流总览
本工作流分为三个核心阶段，接受工作流后按顺序执行：
1. **上下文收集**：收集用户掌握的所有相关背景，通过提问补全信息缺口
2. **细化与结构搭建**：分章节迭代 brainstorm、筛选、起草、优化，完成全文内容
3. **读者测试**：用无前置上下文的全新 Claude 实例测试文档，修复信息盲区和歧义

> [!TIP] 初始offer话术参考
> 主动向用户介绍三阶段工作流，说明该方法能保证文档对读者（包括粘贴到 Claude 的读者）效果更好，询问用户选择使用结构化工作流还是自由创作。

## 详细流程

### 阶段1：上下文收集
**目标：缩小用户和助手的信息差，为后续指导打下基础**

#### 1.1 初始元信息提问
首先询问用户5个基础问题，告知用户可以用简写、任意格式回答：
1. 这是什么类型的文档？（例如技术规格、决策文档、提案）
2. 主要受众是谁？
3. 读者读完后期望达到的影响是什么？
4. 是否有需要遵循的模板或特定格式？
5. 还有其他需要知道的限制或上下文吗？

特殊情况处理：
- 如果用户提到模板或提供了模板：询问是否可以分享模板文档，通过对应集成读取文档内容
- 如果用户要编辑已有的共享文档：用对应集成读取当前文档，检查无替代文本的图片，说明无替代文本会导致 Claude 无法理解图片，询问是否需要生成替代文本，需要则请用户将图片粘贴到对话中生成。

#### 1.2 鼓励信息全量输出
初始问题回答完成后，鼓励用户 dump 所有相关上下文，告知不需要整理，直接输出即可，支持的输出方式包括：
- 意识流式信息输出
- 指向团队频道或对话线程
- 共享文档链接

如果有可用集成（Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务），告知可以直接拉取上下文；如果没有集成且在 Claude Web/APP 端，提示用户可以在设置中开启连接器来直接拉取上下文。

收集过程中的处理规则：
- 用户提到团队频道/共享文档：有集成就直接读取，没有集成则说明无法访问，提示开启连接器或粘贴对应内容
- 用户提到未知实体/项目：询问是否需要搜索已连接工具获取更多信息，得到用户确认后再搜索
- 全程跟踪已获取信息和未明确的信息缺口

#### 1.3 澄清提问与阶段退出
用户完成初始信息输出后，针对信息缺口生成5-10个结构化提问，告知用户可以用简写、链接、指向频道等任意高效方式回答。

当信息足够（可以提问边缘场景和权衡问题，不需要再补充基础信息）后，询问用户是否还有要补充的上下文，确认后进入阶段2。

---

### 阶段2：细化与结构搭建
**目标：分章节通过头脑风暴、筛选、迭代细化完成全文创作**

#### 2.1 确定结构
- 如果文档结构清晰：询问用户想从哪个章节开始，建议从未知信息最多的章节开始（决策文档一般从核心提案开始，规格文档一般从技术方案开始，摘要章节留到最后）
- 如果用户不确定需要哪些章节：根据文档类型和模板推荐3-5个合适的章节，询问是否调整结构

结构确认后，创建带占位符的初始文档框架：
- 如果可以使用 artifacts：调用 `create_file` 创建构件，添加所有章节头和`[To be written]`类占位符，提供构件链接
- 如果不能使用 artifacts：在工作目录创建合适命名的 markdown 文件（例如 `decision-doc.md`），添加所有章节头和占位符，告知用户文件名

#### 2.2 单章节创作流程
每个章节按以下6步迭代：

##### 步骤1：澄清提问
宣布开始创作`[章节名称]`，基于上下文和章节目标生成5-10个具体的澄清问题，告知用户可以简写回答。

##### 步骤2：头脑风暴
针对章节 brainstorm 5-20个可能包含的内容点（根据复杂度调整数量），挖掘之前提到但可能遗漏的上下文、未提及的角度和考虑，最后询问是否需要更多 brainstorm 选项。

##### 步骤3：内容筛选
询问用户哪些点需要保留、删除、合并，要求用户简要说明原因，举例子说明回答格式（例如`保留1,4,7,9`/`删除3（和1重复）`）。如果用户给出自由格式反馈，提取偏好后继续执行。

##### 步骤4：缺口检查
基于用户选择，询问章节是否还有遗漏的重要内容。

##### 步骤5：起草内容
调用 `str_replace` 将占位符替换为起草好的内容：
- 使用 artifacts：起草后提供构件链接，邀请用户阅读并说明修改点
- 使用文件：起草后确认完成，告知用户章节已经写入对应文件，邀请用户阅读并说明修改点
- *首次起草时补充提示：请用户不要直接编辑文档，告知修改点即可，这能帮助助手学习用户的创作偏好*

##### 步骤6：迭代细化
用户提供反馈后，用 `str_replace` 执行修改（不要重新打印整个文档）：
- 使用 artifacts：每次修改后提供链接
- 使用文件：确认修改完成即可
- 如果用户自行编辑了文档并要求读取，记录用户的修改偏好用于后续章节

连续3次迭代没有重大修改后，询问是否可以删除内容来精简文档，用户确认章节完成后进入下一个章节。

#### 2.3 全文档收尾
完成80%以上章节后，宣布要通读全文，检查以下内容：
- 跨章节的流畅性和一致性
- 冗余和矛盾
- 废话和通用填充内容
- 每一句话是否都有信息量

所有章节都完成起草和优化后，再次整体审核一致性、流畅性和完整性，给出最终修改建议，询问用户是进入读者测试还是继续优化。

---

### 阶段3：读者测试
**目标：用无前置上下文的 Claude 测试文档，发现作者盲区**

说明测试的目的：发现作者觉得合理但读者会困惑的内容。

#### 场景A：可使用子代理（例如 Claude Code）
无需用户参与，直接执行测试：
1. **预测读者问题**：生成5-10个读者实际会问的问题
2. **子代理测试**：对每个问题，调用仅传入文档内容和问题的全新子代理，总结子代理回答的正误
3. **额外检查**：调用子代理检查文档的歧义、错误假设、矛盾，总结发现的问题
4. **修复问题**：如果发现问题，反馈具体问题后回到阶段2对应章节优化

#### 场景B：无法使用子代理（例如 Claude Web）
引导用户手动测试：
1. **预测读者问题**：和用户一起生成5-10个读者实际会问的问题（一般是读者会粘贴到 Claude 的问题）
2. **测试准备**：指导用户操作：
   1. 打开全新的 Claude 对话：https://claude.ai
   2. 粘贴/共享文档内容（共享文档开启连接器可直接分享链接）
   3. 让新 Claude 逐个回答预测的问题，要求新 Claude 说明：答案、是否存在歧义、文档假设读者已经掌握哪些知识
3. **额外检查**：让用户请新 Claude 额外回答三个问题：
   - 文档中哪些内容对读者可能有歧义或不清晰？
   - 文档假设读者已经掌握哪些知识或上下文？
   - 文档是否存在内部矛盾或不一致？
4. **修复问题**：询问用户新 Claude 哪些内容回答错误/存在困惑，回到阶段2对应章节优化
